\section{Introduction}%
\label{sec:impl:intro}

\Cref{chap:system} described the system at the level of its design: what each
component does, what it produces, and why it is built that way. A design of this
kind leaves several things to be settled. The components have to be realised
with concrete tools. The simulator, the flight software and the decision code
have to be organised so that they run together. The learned elements have to be
trained before they can be used. Once the system exists, it must also be shown
that it does what the design promises. This chapter addresses both aspects, in
two parts.

The first part covers the implementation. It begins with the technologies and
libraries on which the system is built, and with the machine on which the
missions are run. It then presents the technical architecture, which organises
the simulated warehouse, the vehicles, their flight software and the components
of \Cref{chap:system} into layers, from the physics of the simulation up to the
records produced by a mission. Finally, it presents the learned detector and the
semantic guide.

The second part covers the evaluation. It first defines the protocol, with the
scenarios, the reference methods and the metrics. It then evaluates the main
components, before reporting the results of the missions against the reference
methods. The chapter closes with a conclusion that brings these results together.

\textbf{NVIDIA Isaac Sim}\footnote{\url{https://developer.nvidia.com/isaac/sim}}
is a robotics simulator built on NVIDIA Omniverse. It runs the rigid-body
physics, renders the camera images and simulates the rotating \gls{abb:lidar}.
The warehouse is described as a \textbf{USD}\footnote{\url{https://openusd.org}}
scene.

\textbf{Pegasus
    Simulator}\footnote{\url{https://pegasussimulator.github.io/PegasusSimulator/}}
is an Isaac Sim extension for aerial vehicles. It provides the multirotor model
and the bridge between the simulator and the flight software.

The \textbf{Iris quadrotor} is the vehicle model used for every drone. It is a
four-rotor airframe widely used as a reference in drone simulation.

\textbf{ArduPilot}\footnote{\url{https://ardupilot.org}} is the autopilot
software, run in \glsxtrshort{abb:sitl} (software-in-the-loop) mode. One process
per vehicle flies the drone in GUIDED mode, following the commands sent by the
system.

\textbf{MAVLink}, used through the
\textbf{pymavlink}\footnote{\url{https://github.com/ArduPilot/pymavlink}}
library, is the protocol between the system and the autopilots. It carries the
take-off orders, the velocity commands and the position readings.

\textbf{ns-3}\footnote{\url{https://www.nsnam.org}} is a discrete-event network
simulator. In the network part of the system, it simulates the communication
stack of the radio links, either WiFi (IEEE 802.11n) or 5G NR through the
\textbf{5G-LENA}\footnote{\url{https://5g-lena.cttc.es}} module. It also provides
the latency of each exchange.

\textbf{Sionna}\footnote{\url{https://nvlabs.github.io/sionna/}} is NVIDIA's
library for simulating wireless communication systems. Its ray tracer computes
the radio channel inside the warehouse scene, which gives the signal strength of
each link. The
\textbf{ns3sionna}\footnote{\url{https://github.com/tkn-tub/ns3sionna}} module
couples Sionna with ns-3 through ZeroMQ messages encoded with Protocol Buffers.

\textbf{Python}\footnote{\url{https://www.python.org}} is the implementation
language of the whole system.

\textbf{NumPy}\footnote{\url{https://numpy.org}} and
\textbf{SciPy}\footnote{\url{https://scipy.org}} carry the numerical work. They
compute the layers of the shared map and the candidate targets, and convert
rotations between the frames of the system.

\textbf{OpenCV}\footnote{\url{https://opencv.org}} handles images and camera
geometry, including the pose of a code estimated from its four corners.

\textbf{zxing-cpp}\footnote{\url{https://github.com/zxing-cpp/zxing-cpp}} is the
\glsxtrshort{abb:qr} decoder used in flight.
\textbf{ZBar}\footnote{\url{https://github.com/mchehab/zbar}} and
\textbf{BoofCV}\footnote{\url{https://boofcv.org}} were compared with it on the
same images (Section 4.8.1).

\textbf{Ultralytics}\footnote{\url{https://docs.ultralytics.com}} is the framework
used to train and run the learned detector, which belongs to the YOLO11 family.

\textbf{PyTorch}\footnote{\url{https://pytorch.org}} is the deep-learning
framework on which both the detector and the semantic guide run.

\textbf{Transformers}\footnote{\url{https://huggingface.co/docs/transformers}}
loads the vision-language model of the semantic guide and its processor.

\textbf{bitsandbytes}\footnote{\url{https://github.com/bitsandbytes-foundation/bitsandbytes}}
quantises the guide's model to four bits.

\textbf{PEFT}\footnote{\url{https://huggingface.co/docs/peft}} provides the
low-rank adapter (LoRA) that specialises the guide.

\textbf{qrcode}\footnote{\url{https://github.com/lincolnloop/python-qrcode}} and
\textbf{Pillow}\footnote{\url{https://python-pillow.org}} generate the
\glsxtrshort{abb:qr} images placed on the cartons when a warehouse is built.

\textbf{Matplotlib}\footnote{\url{https://matplotlib.org}} produces the figures,
and \textbf{FFmpeg}\footnote{\url{https://ffmpeg.org}} assembles the mission
videos.

\section{Technical Architecture}%
\label{sec:impl:architecture}

The system is evaluated entirely in simulation, under conditions close to a real
deployment: each drone is flown by genuine autopilot software, and the system
knows only what the drones' sensors measure. \Cref{fig:impl:architecture}
organises the programs involved into seven layers, from the simulated world to
the outputs of a mission. The numbered steps follow one mission cycle.

\subsection*{Layer 1 --- Simulated World}

Isaac Sim computes the physics, renders the camera images and simulates the
\gls{abb:lidar}. The warehouse is produced by a generator from a single integer,
the \emph{seed}. The same seed always yields the same warehouse, and a new seed
yields a new layout, which allows the system to be tested in buildings it has
never seen. The seed sets the position of the racks, the share of shelf positions
holding a carton and the take-off positions of the drones
(\Cref{tab:impl:warehouse}). Empty shelf positions are removed from both the
images and the physics. Each carton carries a \glsxtrshort{abb:qr} code on two
opposite faces, so that it can be read from either aisle. The warehouse of the
nominal scenario contains 114 identifiers on 228 panels.

\subsection*{Layer 2 --- Vehicles}

Pegasus Simulator adds the drones to Isaac Sim, using the Iris quadrotor model.
It also acts as the bridge between Isaac Sim and the autopilots: it sends the
simulated sensor data of each drone to its autopilot and applies the resulting
motor commands. Each drone carries two side cameras, which read the codes on both
sides of an aisle in a single pass. It also carries a \gls{abb:lidar}, whose
distance measurements are used to build the map, and a low-resolution front
camera used by the visual variant of the semantic guide
(\Cref{tab:impl:sensors}).

\subsection*{Layer 3 --- Flight Software}

Each drone is flown by its own ArduPilot process in \glsxtrshort{abb:sitl}
(software-in-the-loop) mode, in which the real flight code runs on the computer
with simulated sensor data. The system never places a drone directly: it sends
commands to the autopilot, which flies with the inertia and small errors of a
real aircraft. Commands travel through MAVLink, the standard autopilot protocol,
and each drone flies in GUIDED mode, in which the autopilot accepts commands from
an external program.

The flight controller turns the pose chosen by the system into velocity commands,
in three phases. During \emph{transit}, the drone follows its route. During
\emph{approach}, it slows down and turns its side camera towards the target.
During \emph{hold}, it stays in place while the cameras observe. A target is
abandoned when the drone stops making progress towards it
(\Cref{tab:impl:flight}).

\subsection*{Layer 4 --- System}

The components of \Cref{chap:system} run in a single loop inside the Isaac Sim
process. Decision-making is decentralised: there is no leader and no central
planner, and every drone selects its own targets. What the drones share is a
single common map, into which they all write their observations and from which
they all read when they decide. Each cycle covers 0.2\,s of simulated time: the
controllers send their commands, Isaac Sim advances the physics, every drone
updates the map, expired claims are removed and at most one drone selects a new
target. Each drone therefore observes five times per second, and the cost of
decisions does not grow with the size of the team.

\subsection*{Layer 5 --- Learned Models}

Two learned models run on the GPU. The YOLO11 detector (Section 4.5) locates
labels and cartons in one side image per cycle, including labels too distant to
be decoded, while the zxing-cpp decoder reads both images. The semantic guide
(Section 4.6), based on Qwen2.5-VL, advises each drone on the area to visit next.
It answers in the background, and its advice is applied to the next decision of
the drone.

\subsection*{Layer 6 --- Network}

Since all observations converge to a single shared map, each drone would, in a
real deployment, send its observations over a wireless link to the point that
holds this map. The network part was developed to evaluate such links, which
always connect two points: two drones, or a drone and a fixed point such as a base
station. Sionna computes the signal strength of a link by ray tracing in a
three-dimensional model of the warehouse, and reports the link as blocked when no
path exists. ns-3 simulates the communication protocols: its nodes follow the
positions of the drones, read continuously from a file, and test packets
exchanged between them give the latency. The ns3sionna module can also provide
ns-3 with the propagation computed by Sionna.

Two configurations were implemented (\Cref{tab:impl:network}). In the 5G
configuration, every drone communicates through a base station placed 6\,m above
the centre of the warehouse, which matches the organisation of the system around a
single map. In the WiFi configuration, the nodes communicate directly with each
other.

\subsection*{Layer 7 --- Outputs}

Each mission is fully recorded, and the system never reads these records while
the mission runs. The record contains the timestamped events, the identifiers
read over time, the decisions and trajectory of every drone, a snapshot of the
map every 10\,s and the camera images used for the videos. After the mission, an
automatic judge compares this record with the \emph{ground truth}, that is, the
true identifier and position of every panel, which the system never accesses. The
judge checks that no drone remained blocked, that no target was pursued by two
drones, that the drones dispersed at the start, that a drone loss was absorbed and
that the mission ended properly. It then measures the identifiers read, the known
share of the building and the safety of the flight. All the results of
Section 4.9 are computed from these records.
