    SwarmScan}%

\section{Introduction}%
\label{sec:impl:intro}

\Cref{chap:system} described the system at the level of its design: what each
component does, what it produces, and why it is built that way. A design of this
kind leaves several things to be settled. The components have to be realised
with concrete tools. The simulator, the flight software and the decision code
have to be organised so that they run together. The learned elements have to be
trained before they can be used. Once the system exists, it must also be shown
that it does what the design promises. This chapter addresses both aspects, in
two parts.

The first part covers the implementation. It begins with the technologies and
libraries on which the system is built, and with the machine on which the
missions are run. It then presents the technical architecture, which organises
the simulated warehouse, the vehicles, their flight software and the components
of \Cref{chap:system} into layers, from the physics of the simulation up to the
records produced by a mission. Finally, it presents the learned detector and the
semantic guide.

The second part covers the evaluation. It first defines the protocol, with the
scenarios, the reference methods and the metrics. It then evaluates the main
components, before reporting the results of the missions against the reference
methods. The chapter closes with a conclusion that brings these results together.

\section{Technologies and Libraries Used}%
\label{sec:impl:stack}

The system is written in Python and runs entirely in simulation. The tools are
presented from the simulator outwards, and \Cref{tab:impl:stack} summarises them
by component.

\textbf{NVIDIA Isaac Sim}\footnote{\url{https://developer.nvidia.com/isaac/sim}}
is a robotics simulator built on NVIDIA Omniverse. It runs the rigid-body
physics, renders the camera images and simulates the rotating \gls{abb:lidar}.
The warehouse is described as a \textbf{USD}\footnote{\url{https://openusd.org}}
scene.

\textbf{Pegasus
    Simulator}\footnote{\url{https://pegasussimulator.github.io/PegasusSimulator/}}
is an Isaac Sim extension for aerial vehicles. It provides the multirotor model
and the bridge between the simulator and the flight software.

The \textbf{Iris quadrotor} is the vehicle model used for every drone. It is a
four-rotor airframe widely used as a reference in drone simulation.

\textbf{ArduPilot}\footnote{\url{https://ardupilot.org}} is the autopilot
software, run in \glsxtrshort{abb:sitl} (software-in-the-loop) mode. One process
per vehicle flies the drone in GUIDED mode, following the commands sent by the
system.

\textbf{MAVLink}, used through the
\textbf{pymavlink}\footnote{\url{https://github.com/ArduPilot/pymavlink}}
library, is the protocol between the system and the autopilots. It carries the
take-off orders, the velocity commands and the position readings.

\textbf{ns-3}\footnote{\url{https://www.nsnam.org}} is a discrete-event network
simulator. In the networked version of the system, it simulates the
communication stack of the vehicle links, either WiFi (IEEE 802.11n) or 5G NR
through the \textbf{5G-LENA}\footnote{\url{https://5g-lena.cttc.es}} module. It
also provides the latency of each exchange.

\textbf{Sionna}\footnote{\url{https://nvlabs.github.io/sionna/}} is NVIDIA's
library for simulating wireless communication systems. Its ray tracer computes
the radio channel inside the warehouse scene, which gives the signal strength of
each link. The
\textbf{ns3sionna}\footnote{\url{https://github.com/tkn-tub/ns3sionna}} module
couples Sionna with ns-3 through ZeroMQ messages encoded with Protocol Buffers.

\textbf{Python}\footnote{\url{https://www.python.org}} is the implementation
language of the whole system.

\textbf{NumPy}\footnote{\url{https://numpy.org}} and
\textbf{SciPy}\footnote{\url{https://scipy.org}} carry the numerical work. They
compute the layers of the shared map and the candidate targets, and convert
rotations between the frames of the system.

\textbf{OpenCV}\footnote{\url{https://opencv.org}} handles images and camera
geometry, including the pose of a code estimated from its four corners.

\textbf{zxing-cpp}\footnote{\url{https://github.com/zxing-cpp/zxing-cpp}} is the
\glsxtrshort{abb:qr} decoder used in flight.
\textbf{ZBar}\footnote{\url{https://github.com/mchehab/zbar}} and
\textbf{BoofCV}\footnote{\url{https://boofcv.org}} were compared with it on the
same images (Section 4.8.1).

\textbf{Ultralytics}\footnote{\url{https://docs.ultralytics.com}} is the framework
used to train and run the learned detector, which belongs to the YOLO11 family.

\textbf{PyTorch}\footnote{\url{https://pytorch.org}} is the deep-learning
framework on which both the detector and the semantic guide run.

\textbf{Transformers}\footnote{\url{https://huggingface.co/docs/transformers}}
loads the vision-language model of the semantic guide and its processor.

\textbf{bitsandbytes}\footnote{\url{https://github.com/bitsandbytes-foundation/bitsandbytes}}
quantises the guide's model to four bits.

\textbf{PEFT}\footnote{\url{https://huggingface.co/docs/peft}} provides the
low-rank adapter (LoRA) that specialises the guide.

\textbf{qrcode}\footnote{\url{https://github.com/lincolnloop/python-qrcode}} and
\textbf{Pillow}\footnote{\url{https://python-pillow.org}} generate the
\glsxtrshort{abb:qr} images placed on the cartons when a warehouse is built.

\textbf{Matplotlib}\footnote{\url{https://matplotlib.org}} produces the figures,
and \textbf{FFmpeg}\footnote{\url{https://ffmpeg.org}} assembles the mission
videos.

\section{Technical Architecture}%
\label{sec:impl:architecture}

The system is evaluated entirely in simulation, but the simulation is designed to
reproduce the conditions of a real deployment. Each drone is flown by genuine
autopilot software, and the system knows only what the drones' own sensors
measure. This requires several programs to run concurrently and to exchange data.
\Cref{fig:impl:architecture} presents their organisation as seven layers, from
the simulated world at the bottom to the outputs of a mission at the top. The
numbered steps follow one cycle of a mission.

\subsection*{Layer 1 --- Simulated World}

Isaac Sim provides the physical world in which the missions take place. It
computes the motion of the rigid bodies, renders the images seen by the cameras
and simulates the \gls{abb:lidar} measurements. The scene, with the building, the
racks and the cartons, is described in USD (Universal Scene Description), the
scene format used by Isaac Sim.

The warehouse is not a fixed model. It is produced by a generator from a single
integer, the \emph{seed}. The same seed always yields the same warehouse, while a
different seed yields a different layout. The seed determines the position of
each rack, the fraction of shelf positions that hold a carton and the take-off
positions of the drones. The dimensions of the building and of the racks remain
constant (\Cref{tab:impl:warehouse}). This mechanism is what allows the system to
be evaluated in warehouses it has never encountered.

When a shelf position is left empty, its carton is removed from the scene
entirely, from both the rendered images and the physics. The \gls{abb:lidar} and
the cameras therefore always observe the same set of objects. Each remaining
carton carries a genuine \glsxtrshort{abb:qr} code on two opposite faces, both
encoding the same identifier, so a carton can be read from either aisle adjacent
to its rack. The warehouse of the nominal scenario, for instance, contains 114
identifiers distributed over 228 panels.

\subsection*{Layer 2 --- Vehicles}

Pegasus Simulator adds the drones to Isaac Sim, and each drone uses the Iris
quadrotor model, a standard airframe in drone simulation. Pegasus also acts as
the bridge between Isaac Sim and the flight software. It transmits the simulated
inertial and position data of each drone to its autopilot, and it applies the
resulting motor commands to the drone in Isaac Sim.

Each drone carries four sensors, configured as shown in \Cref{tab:impl:sensors}:

\begin{itemize}[itemsep=0.35em]
    \item \textbf{Side cameras}: The two side cameras are the reading instruments.
          They point perpendicular to the direction of flight, one to the left and
          one to the right, so that a single pass along an aisle covers the racks on
          both sides. They are mounted slightly below the body to keep the airframe
          out of the images.
    \item \textbf{Front camera}: A low-resolution front camera serves the visual
          variant of the semantic guide.
    \item \textbf{\glsxtrshort{abb:lidar}}: The \gls{abb:lidar} measures the
          distance to the nearest obstacle along a set of rays distributed around
          the drone, and these distances are used to build the map of the building.
          It delivers a complete revolution at each rendered frame, which gives a
          full view of the surroundings at every cycle.
\end{itemize}

\subsection*{Layer 3 --- Flight Software}

Each drone is flown by its own instance of ArduPilot, an open-source autopilot
widely used on real drones. It runs in \glsxtrshort{abb:sitl}
(software-in-the-loop) mode: the flight code executes on the computer as an
ordinary program and receives simulated sensor data instead of real measurements.
The system therefore never sets the position of a drone directly in Isaac Sim. It
sends commands to the autopilot, which flies the drone with the inertia, delays
and small tracking errors of a real aircraft. The behaviour observed in
simulation thus remains close to that of physical drones.

The system communicates with the autopilots through MAVLink, the standard
messaging protocol between an autopilot and a control program. Before a mission,
each drone is connected to its autopilot and waits until the autopilot's position
estimate is reliable. It is then switched to GUIDED mode, in which the autopilot
accepts commands from an external program, before being armed and taking off.
The three drones take off at staggered heights of 1.6\,m, 1.9\,m and 2.2\,m.

During the mission, the flight controller converts the pose selected by the
system (a position and a heading), together with the route leading to it, into
velocity commands for the autopilot. It operates in three successive phases:

\begin{itemize}[itemsep=0.35em]
    \item \textbf{Transit}: The drone follows the waypoints of its route at
          constant speed.
    \item \textbf{Approach}: The speed of the drone decreases in proportion to the
          remaining distance, which prevents it from overshooting into a rack. The
          drone also rotates until its side camera faces the target.
    \item \textbf{Hold}: The drone maintains the pose while the cameras observe. In
          front of a label, the hold lasts 2\,s, which gives ten images to the
          decoder.
\end{itemize}

If the drone makes no progress towards its target for 8\,s, the target is
abandoned and a new one is selected.

\subsection*{Layer 4 --- System}

The components described in \Cref{chap:system} run inside the Isaac Sim process,
within a single loop: perception, the shared map, candidate generation, target
selection and coordination.

Decision-making is decentralised: there is no leader and no central planner, and
every drone runs the same software and selects its own targets. What the drones
share is their knowledge of the building. Each drone writes its observations into
a single common map held by the Isaac Sim process, and reads this map when it
selects a target.

The loop proceeds in cycles of 0.2\,s of simulated time. Within a cycle:

\begin{enumerate}[itemsep=0.2em]
    \item the flight controllers send their commands;
    \item Isaac Sim advances the physics and renders the images;
    \item every flying drone integrates its observations into the map;
    \item expired claims are removed;
    \item at most one drone selects a new target.
\end{enumerate}

Each drone thus receives five observations per second. Since a single drone
decides in each cycle, the computation spent on decisions does not increase with
the size of the team.

\subsection*{Layer 5 --- Learned Models}

Two learned models run on the GPU in support of the system:

\begin{itemize}[itemsep=0.35em]
    \item \textbf{The learned detector} (Section 4.5), from the YOLO11 family,
          locates \glsxtrshort{abb:qr} labels and cartons in the images, including
          labels too distant for their content to be decoded. It processes one side
          camera per cycle, alternating between left and right. The decoder,
          zxing-cpp, extracts the identifiers and processes both images at every
          cycle.
    \item \textbf{The semantic guide} (Section 4.6), based on the Qwen2.5-VL
          vision-language model, advises each drone on the area to visit next.
          Producing an answer takes a few seconds, so the guide runs in the
          background. The drone continues its mission in the meantime, and the
          advice is applied to its next decision.
\end{itemize}

\subsection*{Layer 6 --- Network}

In the system, the observations of all drones converge to a single shared map. In
a real deployment, each drone would therefore have to send its observations over
a wireless link to the point that holds this map. The network part was developed
to evaluate the quality of such links inside the warehouse, where racks and walls
attenuate and block the radio signal. A link always connects two points of the
warehouse, which can be two drones, or a drone and a fixed point such as a base
station. The evaluation relies on two tools with complementary roles:

\begin{itemize}[itemsep=0.35em]
    \item \textbf{Sionna} computes the propagation of the radio signal by ray
          tracing in a three-dimensional model of the warehouse. For the two points
          of a link, it finds the paths followed by the signal, including
          reflections, and derives the received signal strength. When no path
          exists, it reports the link as blocked.
    \item \textbf{ns-3} simulates the communication protocols, from radio access to
          packet transport, and measures the delay with which packets travel from
          one end of a link to the other.
\end{itemize}

Both tools follow the drones during the flight. The positions of the drones are
written continuously to a file, which ns-3 reads to place and move its network
nodes. Test packets are sent between the nodes of the simulated network to
measure latency, while Sionna provides the signal strength of each link. The
ns3sionna module can also make ns-3 take its propagation losses and delays
directly from Sionna. In that case, Sionna runs as a separate server that ns-3
contacts through ZeroMQ messages.

Two network configurations were implemented (\Cref{tab:impl:network}):

\begin{itemize}[itemsep=0.35em]
    \item \textbf{5G}: Every drone communicates through a base station placed 6\,m
          above the centre of the warehouse, operating at 3.5\,GHz with a 20\,MHz
          bandwidth. Each radio link connects a drone to this fixed point, and all
          traffic passes through it. This configuration corresponds to the
          organisation of the system, in which every drone contributes to a single
          shared map.
    \item \textbf{WiFi}: The nodes communicate directly with each other, without
          an access point or a base station.
\end{itemize}

\subsection*{Layer 7 --- Outputs}

Everything that happens during a mission is recorded, and none of these records
is read by the system while the mission runs. A mission record contains:

\begin{itemize}[itemsep=0.2em]
    \item the timestamped events, such as the loss of a drone or the appearance of
          an obstacle;
    \item the number of identifiers read over time;
    \item the decisions, trajectory and attitude of every drone;
    \item a snapshot of the map every 10\,s and the final map;
    \item the camera images from which the mission videos are assembled.
\end{itemize}

Once the mission is over, an automatic judge compares the record with the
\emph{ground truth} of the warehouse, that is, the identifier and true position of
every \glsxtrshort{abb:qr} panel, as produced by the generator. The system never
has access to this ground truth, which is used only by the judge. The judge first
verifies that:

\begin{itemize}[itemsep=0.2em]
    \item no drone remained blocked;
    \item no two drones pursued the same target;
    \item the drones dispersed at the start of the mission;
    \item the loss of a drone, when one occurred, was absorbed by the others;
    \item the mission ended properly.
\end{itemize}

It then measures the identifiers read, the share of the building that became
known and the safety of the flight. All the results reported in Section 4.9 are
computed from these records.
